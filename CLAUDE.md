# Living City: read me first (every session)

Living City is a Garry's Mod Half-Life 2 roleplay gamemode. The owner has put a great deal into it and runs it on a live server. **Before changing anything, read `CORE.md`** (the core: the owner's server, where their files are, what must not change without asking) and `HANDOFF.md` (the latest work). Both are short. **Read nothing else unless the task needs it:** `README.md` is only an index to `docs/features/` (one file per feature: open just the one you are changing); `TIMELINE.md` (every earlier chat, in date order) and `CORE_CHANGELOG.md` (approved core changes) are history, read on demand only. Never read `PLAYER_TEXT.md`, `_dev/core_snapshot.txt`, `_dev/rewording/` or `livingcity_sound/` (they are in `.clineignore`, and all but the core snapshot are also blocked in `.claude/settings.json`; the snapshot is left open there so a command can sort or update it with the owner's OK, but still never read it whole); use `grep` or `diff` in a shell when you need a line from one.

## The one rule above all

**Nothing the owner relies on changes unless they asked for it, or you asked them first and they said yes.** That means anything in `CORE.md` and any behaviour `docs/features/` describes: where files are read from, file names, settings and their defaults, factions and ranks, items, commands, how a feature behaves. A new feature is fine. A change to an existing one, even a "fix" or a tidy-up, is first described to the owner in plain words ("this would change X to Y: OK?"). The test "the core is as the owner knows it" fails when the core changes: tell the owner what it printed, and update `_dev/core_snapshot.txt` only with their OK (`CORE.md`, rule 4).

**When something isn't working on their server, find out what's there before touching the code**: ask for the debug report, `lc_announce_clips`, `lc_endings` or `lc_sound_check`, and compare it with `CORE.md`. Make the code fit their setup; never ask them to rename or move their files to fit a guess.

## House rules (the owner insists on these)

1. **Never use em dashes**, anywhere (code, comments, docs, commits, chat). `grep -rl $'\xe2\x80\x94' . --exclude-dir=.git` must print nothing.
2. **Everything works through the in-game UI.** Console commands are extras for admins, never the only way. Important messages go through `LC.Notice`. **Never put anything only in the C menu** (the owner, 10 November: "please STOP ADDING THINGS EXCLUSIVELY TO THE C MENU"): every new action goes on F1, F2 or F4 first; the C menu may repeat it. **One exception (the owner, 13 November):** a unit's calls to Combine HQ (backup, resupply, BOLO, 10-20, records, sweeps, directives) go ONLY on the radio's own menu (radio out, right click), never on F1, F2, F4 or the C menu; F2 keeps what's done on the spot.
3. **Every task keeps these up to date, in one batched pass at the end (not after each change):** the touched file(s) in `docs/features/`, the playtest card (`PLAYTEST.md`: only what a person must judge, see below), the guide in `gamemodes/livingcity/gamemode/cl_init.lua` (when players would notice), and `CORE.md` + `CORE_CHANGELOG.md` when it touches the core. `_dev/tests.lua` and `_dev/client_smoke.py` go with the code. When text players see changed, run `python3 _dev/player_text.py` once at the end: it makes `PLAYER_TEXT.md` (every line a player sees, for the owner to correct). **Never hand-edit `PLAYER_TEXT.md`.**
4. **Commit messages** say what changed in plain words, and end with the session's attribution lines. No model names or IDs in commits or code.
5. **Work lean.** The owner has a limited budget: keep chat short, don't re-read large files you don't need. When a task is done, rewrite "Where things stand" in `HANDOFF.md` (15 lines or fewer). **Never tell the owner to start a new chat** (the owner, 9 November: they never asked for that rule); keep working in the chat they are in.
6. **Deliver a zip after each change:** `git archive HEAD` into a temp `livingcity/`, remove `livingcity/livingcity_sound`, `livingcity/pose_recorder`, `livingcity/materials`, `livingcity/resource` and `livingcity/_dev`, zip it as `livingcity.zip`, send it as a file (Hexane refuses to unzip `.sh` files). Only when something in `_dev/tools/` changed, also send `livingcity_tools.zip` (`livingcity/_dev/` alone, for the owner's PC, never the server). Only when a picture or the font changed, also send `livingcity_content.zip`: `git archive HEAD materials resource/fonts/lcrebelhand.ttf resource/fonts/lcrebelhand_LICENSE.txt` as a zip, unzipped in the server's `garrysmod/` (`CORE.md`: FastDL never looks in `addons/`). Never send a sound zip that could replace the owner's sound folders.
7. The owner plays on **Linux Mint**: give Linux commands.
8. **`main` is the official branch** (the owner, 2026-10-16: "stop using random branches"). Start from `main`. When a change is finished and the tests pass, push it to the session's branch and also to `main` (a fast-forward: `git push origin HEAD:main`; if `main` has moved, merge it in first, never force).
9. **No "stand here" job steps, ever** (the owner, 14 November: "STOP HAVING QUESTS OF 'stand', as in standing in a spot doing nothing ... make minigames, make something scripted happen, SOMETHING"). No job, shift or story step may be standing, staying, crouching or waiting in a spot for N seconds (the quest `hold` stage, `Q.Hold`, a `survive` or timer used that way, "stay next to it to repair it"). Use instead: a minigame (`Q.GameGo` with the job games: wiring, papers, the line, triage, rubble...), a search by hand (`LC.QuestSearchStage`: hold E on real things, one hides what's wanted), an interrogation or conversation (`LC.NPCInterrogationStart`), a chase or arrest, or something scripted that happens and must be answered (the cells' riot, a counterattack). **The exception (the owner, 14 November):** holding ground against attacks or waves of a counterattack, a unit's checkpoint or post, and holding a zone or territory you attacked or raided may stay timed. The older ones were replaced on 14 November (`docs/features/jobs-and-quests.md`).
10. **Keep what players read to a minimum** (the owner, 14 November: "keep the gamemode minimalistic in terms of text the player sees ... you as an AI have a tendency to overwhelm everything with text and have 20 different instructions and threads on the screen popping up constantly and I can only read one at a time"). One thing on screen at a time, in as few words as will do. Before adding a chat line, notice, hint, card, objective or popup, ask whether the world can show it instead (a sound, an animation, a person saying it) or whether it can go entirely; prefer changing an existing line to adding a new one. No stacked notices, no repeated reminders, no paragraph where a sentence will do, no instructions for things the player can figure out. When in doubt, leave it out.

## Reading budget (every chat re-sends everything it has read, so read narrowly)

1. **Never open a file over about 20 KB whole.** Most of `modules/server/` and `modules/client/` is bigger, and `_dev/tests.lua` is 1.7 MB, `PLAYTEST_ARCHIVE.md` 280 KB, `TODO.md` 60 KB, `TIMELINE.md` 59 KB. Find the spot with `grep -n 'function LC.Name' FILE | cut -c1-160`, then read only that line range. Check sizes with `wc -c` first when unsure.
2. **Start from the code map, not from exploring, and never read it whole (30 KB).** `python3 _dev/make_modules_map.py --module NAME` prints one module's row (server, client and shared files, key functions, the tests that cover it) and, for every file over 20 KB, an outline of `start-end name` lines for each top-level function, hook and section. Add `--grep TEXT` to narrow it (`--module quests --grep Story`); `--outline PATH` does any Lua file. Then read only that range: `sed -n 'A,Bp' PATH`. To find a feature by a word: `grep -n TEXT docs/dev/modules.md | cut -c1-300`. Ranges come from the file as it is now, so rerun the command after editing the file. The map itself is generated by `python3 _dev/make_modules_map.py`: rerun it after adding a module or a test unit, never hand-edit it.
3. **Web pages: fetch only a `.md` or plain-text version, with a narrow question** (for example the raw file, or the page's `.md` URL), and never paste a whole page into the chat. Say in the question what you want back (a signature, one setting, one example).
4. **`PLAYTEST.md` is a short card (the owner, 14 November): about 15 things only a person can judge**, how it looks, sounds and feels, in the order of one walk through a session. What a test can prove gets a test (or a robot player, `_dev/robots.py`), never a line on the card. A new thing a person must judge goes on the card while it has room; when it is full, at the end of `PLAYTEST_ARCHIVE.md` with the tag `[needs a person: why]`: `printf '%s\n' '- [ ] **Topic:** what to try. [needs a person: why]' '  Notes:' >> PLAYTEST_ARCHIVE.md`. When the owner has ticked the card, cut the next one from the archive's newest `[needs a person` and `[needs the real server` items. **`TODO.md`: append with a shell command; don't read it:** `printf '%s\n' '- [ ] **Topic:** what is open.' >> TODO.md`.
5. **`PLAYTEST_ARCHIVE.md` (the old list, 280 KB, every item tagged) and `TODO.md`: never whole.** `grep -n '^## ' FILE | cut -c1-100` for the headings, then `sed -n 'A,Bp' FILE`, or `tail -n 60 FILE` for the newest entries; `grep -n 'needs a person' PLAYTEST_ARCHIVE.md | cut -c1-160` for what still waits on the owner.
6. **Never read `_dev/tests_index.txt` whole (15 KB):** `grep -n TEXT _dev/tests_index.txt | cut -c1-160`.

## Testing

- Client smoke test, from the repo root: `python3 _dev/client_smoke.py` (must end `CLIENT SMOKE PASS`).
- **One section or unit: `python3 _dev/run_section.py "part of the section name"` or `python3 _dev/run_section.py --unit NameTests`** (from the repo root; about 12 to 30 seconds). It builds a trimmed copy of `tests.lua` with the same line numbers, runs it, writes the full output to `/tmp/livingcity_sections/NAME.out.txt` and prints only the target's pass/fail count and its FAIL lines. A section inside a `XTests()` unit runs as the whole unit. Find names with `python3 _dev/run_section.py --list TEXT` (or `grep -n TEXT _dev/tests_index.txt`; regenerate the index with `--index` after adding sections). If it prints `NEEDS STATE` and the run fails, a local the section borrows from an earlier one is built by real code: rerun with `--borrow-all` (or `--also A-B` for a few lines of `tests.lua`). Look into the output file only with `grep -n 'FAIL\|Traceback\|LuaError' FILE | cut -c1-200`.
- Full suite, from `_dev`: `timeout 6900 python3 run_tests.py tests.lua` (about 40 minutes; run it in the background, redirect to a file, read only its tail). It includes the core snapshot check.
- **Full suite on every core: `python3 _dev/run_parallel.py`** (from the repo root; a few minutes instead of 40+). It cuts `tests.lua` into about 16 shards the way `run_section.py` does (the gamemode load and the locals a shard borrows go with it), runs them at once (`--workers N`, default the CPU count) and prints every FAIL line with its section, the core snapshot check (once, writing `_dev/core_snapshot.new.txt` as `run_tests.py` does) and the same last line, `N passed, M failed`. A shard that crashes counts one failure and the rest of it runs again. `--dry-run` lists the shards and atoms, `--atoms I-J` runs a few to look into one, `--save-times` updates `_dev/test_times.json` (what the cut is balanced by). A test that needs what an earlier one left goes in `KEEP_TOGETHER` (or `SETUP`) in `run_parallel.py`. Some tests are random (Lua's table order changes from run to run), so a FAIL that comes and goes is not the sharding: check it with `run_section.py`. **`run_parallel.py` is the run to trust** (since 14 November): every shard starts from a fresh city. The one-piece `run_tests.py tests.lua` currently stops partway (what one test leaves behind upsets a later one: `TODO.md`).
- **The robot players: `python3 _dev/robots.py`** (from the repo root; about a minute and a half; `--quiet` for the summary only). A fake player takes every job on the boards for each side it is offered to, every part of every story and every Union shift, and does it the way a player would (walks there, uses the thing, makes the arrest, holds E on what is to be searched, answers the choice). A job passes when it finishes and pays. Each is done twice, the second time with the game's hooks answering in the other order: a job that goes differently depends on which piece of code hears a key press first, which the game does not promise. What the robot cannot do yet is listed as "robot can't", never counted as done. Run it after touching a job, a quest stage, a story or a job game. `docs/dev/robot-players.md`.
- **The house rules as numbers: `python3 _dev/house_rules.py`** (also the first thing `run_tests.py` and `run_parallel.py` do). It counts the stand-still job steps (rule 9), the places that put text on a player's screen (rule 10) and the console commands no menu names (rule 2), against `_dev/house_rules.json`. They may fall, not rise: a rise fails the run. `--list` prints what was counted; `--update` writes a new baseline (only for one of the owner's exceptions, or a line that is truly needed: say which in the commit).
- **`LC.Try`, never `pcall`, in the gamemode:** what it swallows goes in the server's errors file (`CORE.md`). A bare `pcall` fails the run's first check. Tests may use `pcall`.
- **`tests.lua` must load whole:** its main level is one Lua function, and Lua allows 200 local variables in one. A section run or a shard has fewer and still loads, so the runners now say `TESTS.LUA DOES NOT LOAD WHOLE` when the full file no longer does. Put a new test in its own scope: `function NameTests() ... end NameTests()`, or `;(function() ... end)()`.
- The owner asked to test less: run only the section you touched, the full suite when they ask (`HANDOFF.md`, "Testing").
